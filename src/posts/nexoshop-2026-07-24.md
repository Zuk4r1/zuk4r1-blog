# 🛒 NexoShop: Creando un laboratorio para entender las vulnerabilidades de lógica de negocio

En el mundo de la seguridad web, muchas vulnerabilidades críticas no aparecen por errores clásicos como SQL Injection o Cross-Site Scripting.

Existen fallos mucho más difíciles de detectar porque dependen de entender cómo funciona una aplicación: sus reglas, procesos internos y validaciones.

Estas vulnerabilidades son conocidas como **Business Logic Vulnerabilities** y representan uno de los mayores retos dentro de áreas como:

- Bug Bounty
- Pentesting Web
- Application Security (AppSec)

Un atacante no siempre necesita romper una tecnología; muchas veces basta con encontrar una suposición incorrecta dentro del flujo de negocio.

---

# 🚀 Presentando NexoShop

Como parte de mi aprendizaje en seguridad ofensiva, desarrollé **NexoShop — Business Logic & Broken Access Control Lab**, una aplicación web deliberadamente vulnerable diseñada para practicar análisis de lógica de negocio en un entorno controlado.

Repositorio del proyecto:

🔗[NexoShop](https://github.com/Zuk4r1/business-logic-vulnerability-lab)

El objetivo principal fue crear una aplicación similar a un comercio electrónico real y posteriormente auditarla con mentalidad de atacante:

**Construir → Romper → Analizar → Documentar**

# 🏗️ Arquitectura del laboratorio

NexoShop fue desarrollado utilizando una arquitectura sencilla para facilitar el análisis de cada vulnerabilidad:

| Componente | Tecnología |
|---|---|
| Backend | Python + Flask |
| Base de datos | SQLite |
| ORM | Flask-SQLAlchemy |
| Frontend | Jinja2 + Bootstrap 5 |
| Contenedores | Docker + Docker Compose |

La aplicación incluye funcionalidades comunes de una tienda online:

- Catálogo de productos.
- Sistema de usuarios.
- Carrito de compras.
- Aplicación de cupones.
- Checkout.
- Billetera interna.
- Historial de pedidos.
- Gestión de perfil.

# 🔥 Vulnerabilidades implementadas

## 1. Manipulación de cantidades negativas

Una de las vulnerabilidades implementadas consiste en una validación incorrecta del valor enviado para la cantidad de productos.

La aplicación asumía que una cantidad siempre sería positiva, permitiendo modificar la lógica del cálculo:

```bash
subtotal = precio × cantidad
```

Cuando una aplicación confía en estas suposiciones sin validar correctamente los datos, el flujo financiero puede verse comprometido.

### Impacto:

Manipulación del valor final de una compra.
Alteración del cálculo económico.
Abuso del proceso de checkout.

## 🎟️ 2. Abuso de cupones de descuento

El sistema incluye diferentes códigos promocionales:

| Código | Descuento |
|--------|-----------|
| `BIENVENIDA10` | 10% |
| `VERANO15` | 15% |
| `VIP5` | 5% |
| `BLACKFRIDAY20` | 20% |
| `NEWSLETTER8` | 8% |

El fallo aparece cuando la aplicación permite aplicar descuentos sin controles suficientes sobre la cantidad o combinación de cupones.

### Impacto:

Descuentos superiores a los permitidos.
Manipulación del precio final.
Pérdidas económicas en escenarios reales.

## ⏱️ 3. Race Condition en operaciones financieras

Las condiciones de carrera ocurren cuando múltiples procesos acceden al mismo recurso al mismo tiempo sin una sincronización adecuada.

En este laboratorio se simula una operación de retiro donde:

Se consulta el saldo disponible.
Se valida la operación.
Se actualiza el saldo.

Si varias solicitudes ocurren simultáneamente, pueden producir resultados inesperados.

### Impacto:

Operaciones duplicadas.
Inconsistencia de datos financieros.
Alteración del estado de la cuenta.

## 🔐 4. Broken Access Control / IDOR

Otra vulnerabilidad incluida es un fallo de autorización basado en referencias directas a objetos.

El problema aparece cuando una aplicación valida que un usuario esté autenticado, pero no verifica correctamente si tiene permiso sobre el recurso solicitado.

Pregunta clave durante una auditoría:

¿El usuario autenticado realmente debería poder acceder o modificar este recurso?

### Impacto:

Acceso no autorizado a información.
Manipulación de recursos pertenecientes a otros usuarios.

## 🧪 Metodología aplicada

Durante el desarrollo del laboratorio se aplicó una metodología similar a una auditoría real:

Reconocimiento

Identificación de rutas, funcionalidades y flujo de negocio.

Análisis

Evaluación de posibles puntos donde la aplicación asumía datos confiables.

Explotación controlada

Pruebas sobre parámetros, autorizaciones y lógica interna.

Documentación

Registro del hallazgo, impacto y posibles mitigaciones.

## 📚 Relación con OWASP

Las vulnerabilidades implementadas están relacionadas con categorías del:

OWASP Web Security Testing Guide (WSTG)

Business Logic Testing
Authorization Testing
Broken Access Control

Estas categorías requieren más análisis manual que herramientas automatizadas, ya que dependen del contexto de la aplicación.

## 🛡️ Lecciones aprendidas

Durante la creación de este laboratorio pude reforzar varios conceptos:

✅ Las vulnerabilidades más interesantes no siempre están en el código más complejo.

✅ Una validación de negocio incorrecta puede tener mayor impacto que un fallo técnico tradicional.

✅ Los controles de autorización deben validar siempre la relación entre usuario y recurso.

✅ Crear laboratorios propios ayuda a desarrollar la mentalidad necesaria para Bug Bounty y Pentesting.
